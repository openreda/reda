# Packaging, signing and auto-updating a Rust desktop app

Research for issue #24. Researched 2026-11-01 against tool documentation and source, Apple and Microsoft platform documentation, the Azure retail price API, Flathub's requirements and the release pipelines of other open-source Rust desktop apps. Prices and eligibility rules change; the dates and sources below say when each was read.

## Answer in brief

- **Packaging tool:** use **cargo-packager** (MIT/Apache-2.0, maintained by CrabNebula). It builds the GUI formats REDA needs from one config: `.app` and `.dmg` on macOS, NSIS `.exe` and WiX `.msi` on Windows, `.deb`, AppImage and a pacman PKGBUILD on Linux. It also writes file associations into each format. **cargo-dist** (`dist`) does not fit a GUI app yet: it makes tarballs, shell and PowerShell installers, npm, Homebrew and MSI, and lists "macOS dmg / app" and Flatpak only as future installers.
- **macOS:** signing and notarization are effectively mandatory. They need the Apple Developer Program (99 USD a year), a Developer ID Application certificate, the hardened runtime and a secure timestamp, then `notarytool` and stapling. Since macOS Sequoia, users can no longer Control-click past Gatekeeper; they must go to System Settings for an unnotarized app.
- **Windows:** signing is strongly advisable. Unsigned and self-signed files get "Windows protected your PC", and Smart App Control on Windows 11 blocks unsigned files outright. EV certificates no longer skip SmartScreen, so the cheapest public-trust route is Microsoft's **Artifact Signing** (formerly Trusted Signing) at 9.99 USD a month. Its catch is that individual developers must live in the US or Canada; elsewhere it needs a registered organization. The alternatives are the **Microsoft Store**, where registration is free for individuals and Microsoft re-signs the app so it never sees SmartScreen, **SignPath Foundation** (free for OSS, but the certificate names SignPath Foundation as publisher) and commercial cloud-HSM certificates.
- **Linux:** no OS signing is needed. Ship **Flatpak via Flathub**, which builds from source offline and delivers updates itself. Add AppImage and `.deb` as direct downloads.
- **Auto-update:** use **cargo-packager-updater**. It verifies a minisign signature against a public key built into the app, independently of HTTPS and of the OS code signature, and handles `.app`, AppImage, NSIS and MSI. **Velopack** is the stronger alternative if delta updates matter, but it verifies only SHA checksums taken from the same feed and needs the .NET SDK for its `vpk` CLI.
- **File types:** `.reda`, `.redasch` and `.redapcb` become `CFBundleDocumentTypes` plus exported UTIs on macOS, ProgIDs on Windows and a shared-mime-info XML plus `MimeType=` in the `.desktop` file on Linux. cargo-packager's `file_associations` covers the first two and the `.desktop` side; REDA has to ship the MIME XML itself.

## Recommendation for REDA

1. **Now (pre-alpha):** publish unsigned archives on GitHub Releases from a GitHub Actions matrix (Linux, Windows and macOS runners). Write no auto-updater; at most add an in-house "a newer version exists" check against the GitHub Releases API that opens the browser. This adds no dependency and needs no secrets.
2. **First public release:** add cargo-packager to CI for `.dmg`, NSIS/MSI, `.deb` and AppImage, with file associations. Join the Apple Developer Program and sign and notarize with an App Store Connect API key. For Windows, take Artifact Signing if the developer or an organization qualifies; otherwise use the Microsoft Store as the signed channel and keep the direct download unsigned (or apply to SignPath Foundation). Submit a Flatpak to Flathub.
3. **When update friction matters:** add cargo-packager-updater with a minisign key kept in CI secrets, served from a static JSON file on GitHub Releases or Pages. Linux Flatpak users update through Flathub, and the in-app updater should stay off there.

Expected running cost: 99 USD a year for Apple, plus 9.99 USD a month (about 120 USD a year) if Artifact Signing is used. The total is about 220 USD a year, or 99 USD with the Store or SignPath route.

## macOS: signing and notarization

- **Requirement.** "Beginning in macOS 10.15, all software built after June 1, 2019, and distributed with Developer ID must be notarized." The notary service requires every executable to be code-signed with a **Developer ID** certificate, the **hardened runtime** enabled, a **secure timestamp**, no `get-task-allow` entitlement and linking against the 10.9 SDK or later. You submit with `notarytool` (`altool` was retired on 2023-11-01) and staple the ticket to the `.app`, `.dmg` or `.pkg`. ([Apple: Notarizing macOS software](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution))
- **Cost.** "The Apple Developer Program is 99 USD per membership year." ([Apple](https://developer.apple.com/programs/whats-included/))
- **User impact if skipped.** In macOS Sequoia, users can no longer Control-click to override Gatekeeper for software that is not signed correctly or notarized; they must allow it in System Settings → Privacy & Security. This was an Apple developer announcement of August 2024, reported e.g. by [The Hacker News](https://thehackernews.com/2024/08/apples-new-macos-sequoia-tightens.html) and [pxlnv](https://pxlnv.com/linklog/macos-sequoia-gatekeeper/).
- **CI secrets.** These are the Developer ID certificate as a base64 `.p12` and its password, plus an App Store Connect API key (`.p8`, key ID, issuer ID) for `notarytool`. Zed's `script/bundle-mac` uses exactly `MACOS_CERTIFICATE`, `MACOS_CERTIFICATE_PASSWORD`, `APPLE_NOTARIZATION_KEY`, `APPLE_NOTARIZATION_KEY_ID` and `APPLE_NOTARIZATION_ISSUER_ID`. It imports the certificate into a temporary keychain and runs `codesign --timestamp --options runtime` on each binary, then on the bundle. ([zed/script/bundle-mac](https://github.com/zed-industries/zed/blob/main/script/bundle-mac))
- **Signing without a Mac.** `rcodesign` (the `apple-codesign` crate) signs Mach-O, bundles, `.pkg` and `.dmg`, notarizes and staples from Linux or Windows ([apple-codesign docs](https://gregoryszorc.com/docs/apple-codesign/main/)). Neovide signs with its GitHub Action `indygreg/apple-code-sign-action`. Its last release is 0.29.0 (2024-11-29), so it works but is quiet. GitHub's macOS runners are free for public repositories anyway, so REDA can use Apple's own tools.

## Windows: signing and SmartScreen

- **What signing buys.** Microsoft's guidance: unsigned and self-signed files get "Windows protected your PC" and need "Run anyway". OV- and EV-signed files still show "unrecognized" until reputation builds, but display the verified publisher, and later releases signed with the same identity inherit reputation. "EV certificates no longer bypass SmartScreen … Paying a premium for EV solely to avoid SmartScreen warnings is no longer justified." Smart App Control on Windows 11 "will block execution of unsigned files unless the file has a positive reputation". Store-distributed apps "are re-signed by Microsoft and carry full reputation". ([Microsoft: SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation), updated 2026-08-17)
- **Artifact Signing (formerly Trusted Signing).** Basic costs 9.99 USD a month with 5,000 signatures; Premium costs 99.99 USD a month with 100,000; overage is 0.005 USD a signature ([Azure retail prices API](https://prices.azure.com/api/retail/prices?$filter=contains(productName,'Signing')), queried 2026-11-01; [pricing page](https://azure.microsoft.com/en-us/pricing/details/artifact-signing/)). It requires a paid Azure subscription, not a free or trial one. It issues no EV certificates, and the private key never leaves Microsoft's HSM. ([FAQ](https://learn.microsoft.com/en-us/azure/artifact-signing/faq))
  - **Eligibility:** "Public Trust certificates are available to organizations in the United States, Canada, the European Union, the United Kingdom, Australia, New Zealand, Japan, South Korea, Singapore, Switzerland, Norway, and Israel. Individual developers must be located in the United States or Canada." Organization validation takes 1–20 business days and needs a legal entity, its own domain email and a business identifier. ([Quickstart](https://learn.microsoft.com/en-us/azure/artifact-signing/quickstart))
  - **CI:** dist and Velopack both support it directly. dist uses `AZURE_CLIENT_ID`, `AZURE_TENANT_ID` and `AZURE_SUBSCRIPTION_ID` with GitHub OIDC, so no long-lived secret is needed. Zed signs its Inno Setup installer with Azure credentials ([bundle-windows.ps1](https://github.com/zed-industries/zed/blob/main/script/bundle-windows.ps1)).
- **Microsoft Store.** Since September 2025, individual developers register for free in nearly 200 markets, and Win32 apps are accepted ([Windows Developer Blog](https://blogs.windows.com/windowsdeveloper/2025/09/10/free-developer-registration-for-individual-developers-on-microsoft-store/), [Learn](https://learn.microsoft.com/en-us/windows/apps/publish/whats-new-individual-developer)). The Store is the only route that avoids SmartScreen from the first download, and it delivers updates.
- **SignPath Foundation.** Free for OSS. "The code signing certificate is issued to SignPath Foundation", so the publisher shown is SignPath Foundation, not REDA. It requires an OSI licence for all components, no proprietary component, verifiable builds from source, and "Every release needs manual approval for signing". ([signpath.org/terms](https://signpath.org/terms))
- **Commercial OV certificates.** Since the CA/Browser Forum's 2023 rules, keys must live in an HSM, so in practice this means a cloud signing service such as SSL.com eSigner, which dist supports. These cost more than Artifact Signing and gain nothing on SmartScreen.

## Linux

- **Flathub:** "All source available submissions must be built entirely from source code" and "There is no network access during the build process", so Cargo crates must be vendored as manifest sources (the usual tool is flatpak-builder-tools' `flatpak-cargo-generator`). Flathub also needs a validated MetaInfo file and a reverse-DNS app ID on a domain the project controls, verified with a `.well-known/org.flathub.VerifiedApps.txt` token. Portals are mandatory where one fits, which suits `rfd` (it uses the XDG file-chooser portal). ([Flathub requirements](https://docs.flathub.org/docs/for-app-authors/requirements)) Flathub signs its repository and ships updates, so no in-app updater is needed.
- **AppImage and `.deb`:** cargo-packager makes both. Build on an old-glibc base so the AppImage runs on older distros. Neither needs signing; an apt repository would need a GPG key, but direct `.deb` downloads do not.
- Zed ships a Flatpak (`script/flatpak`) and a tarball with `install.sh`. Lapce ships `.deb` and `.rpm` from CI.

## Auto-update options and trust models

| Option | Verifies | Trust anchor | Fit |
|---|---|---|---|
| cargo-packager-updater | minisign signature of the artifact (`minisign-verify`); HTTPS enforced on main since 2026-10-12 | Public key compiled into the app; private key in CI | Best fit. Survives a compromised download host; formats `app`, `appimage`, `nsis`, `wix`; endpoint JSON with `{{target}}`/`{{arch}}` placeholders, 204 = no update |
| Velopack | Size + SHA1/SHA256 from the releases feed (`verify_package_checksum` in `lib-rust/src/manager.rs`) | Whoever controls the feed host + TLS | Delta updates and a polished installer; no independent signature; .NET SDK in CI |
| axoupdater (dist) | Reruns dist's installer from GitHub Releases | GitHub + TLS | Made for CLI installs; not for `.app`/MSI GUI installs |
| Own HTTPS endpoint (Zed) | TLS only, then platform code signing on the new bundle | Server + TLS + OS signature | Zed's `auto_update` crate fetches `/releases/{channel}/{version}/asset` from its server |
| Store / Flathub | The store's own signing | Microsoft / Flathub | Free updates; no in-app code |

Sources: [cargo-packager-updater docs](https://docs.rs/cargo-packager-updater/latest/cargo_packager_updater/) and the commit `feat(updater): enforce secure (HTTPS) transport` (2026-10-12) in the cargo-packager repo; Velopack source [`src/lib-rust/src/manager.rs`](https://github.com/velopack/velopack/blob/develop/src/lib-rust/src/manager.rs); [dist updater](https://axodotdev.github.io/cargo-dist/book/installers/updater.html); Zed [`crates/auto_update/src/auto_update.rs`](https://github.com/zed-industries/zed/blob/main/crates/auto_update/src/auto_update.rs).

Trust model in short: TLS alone means anyone who controls the release host can push code. An update signature with a key built into the app (minisign, or EdDSA as in Sparkle on macOS) limits that to whoever holds the signing key. OS code signing adds a publisher identity but is checked by the OS only at launch, not by the updater, unless the updater checks it explicitly. REDA should sign updates with minisign and keep the key only in CI secrets.

## File-type associations for `.reda`, `.redasch`, `.redapcb`

- **macOS:** declare `CFBundleDocumentTypes` (role Editor) and export UTIs (`UTExportedTypeDeclarations`, conforming to `public.json`/`public.text`) in `Info.plist`. Opening a file arrives as an Apple Event, not as `argv`, so the app must handle `application:openURLs:`; check how winit/eframe surface this before relying on it for open-from-Finder. cargo-packager's `FileAssociation` maps `name` → `CFBundleTypeName` and `role` → `CFBundleTypeRole`.
- **Windows:** register a ProgID (e.g. `REDA.Schematic.1`) under `Software\Classes` with `FriendlyTypeName`, `DefaultIcon` and `shell\open\command`, and point `.redasch` at it ([Microsoft: Programmatic Identifiers](https://learn.microsoft.com/en-us/windows/win32/shell/fa-progids), [How to register a file type](https://learn.microsoft.com/en-us/windows/win32/shell/how-to-register-a-file-type-for-a-new-application)). The installer does this; cargo-packager's `description` sets the Explorer "Type" column.
- **Linux:** install a shared-mime-info XML (e.g. `application/x-reda-schematic` with glob `*.redasch`) into `share/mime/packages/` and list the types in the `.desktop` file's `MimeType=` ([shared-mime-info spec](https://specifications.freedesktop.org/shared-mime-info/latest/), [Desktop Entry spec](https://specifications.freedesktop.org/desktop-entry-spec/latest/)). cargo-packager takes a `mime_type` per association for the `.desktop` entry. The MIME XML must be shipped too, and Flatpak exports it from `/app/share/mime/packages`. A plain AppImage cannot register types on its own without an integration tool.
- Since every Document is JSON (ADR-0005), declaring each type as a subtype of JSON lets other tools preview the files. Note that `.reda/` is also the cache directory name in ADR-0005; this is harmless for associations, which match files only.

## Open questions

- Whether REDA (or its developer) can pass Artifact Signing validation depends on the developer's country and on whether an organization is registered. This decides between Artifact Signing, the Store and SignPath for Windows.
- The app ID and domain for Flathub and macOS bundle IDs (e.g. `org.openreda.Reda`) need a domain the project controls.
- cargo-packager's last tagged release is a year old even though main is active; pin a git revision or wait for 0.12 if the HTTPS-enforcing updater change is wanted.
